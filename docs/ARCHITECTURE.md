# Architecture and technical implementation

bbtube has two halves. Both are small enough to read in one sitting:

| Part | File | Size | Language |
|---|---|---|---|
| Phone app | `src/BBTube.java` | ~1,360 lines | Java ME: MIDP 2.0, CLDC 1.1, JSR‑135, Java 1.3 syntax |
| Mac server | `bbtube.py` | ~460 lines | Python 3 standard library |

```
 ┌──────────── BlackBerry Bold 9780 (OS 6) ────────────┐        ┌──────────────── Mac ────────────────┐
 │                                                     │  Wi‑Fi │                                     │
 │  bbtube MIDlet                                      │  HTTP  │  bbtube.py  :8090                   │
 │   ├─ Screen (Canvas)  Home / Results / Video /      │◀──────▶│   ├─ /app/bbtube.jad|jar  install   │
 │   │                   Preview                        │        │   ├─ /api/search|video|thumb|play   │──▶ Invidious :3000
 │   ├─ VideoScreen (Canvas) + MMAPI Player ───────────│────────│──▶├─ /v/ID.mp4  (Range, 206)        │      (Docker)
 │   ├─ Form  Options                                  │        │   ├─ /frame  storyboard crops       │
 │   └─ RecordStore  server address, recent searches   │        │   ├─ /log    phone → bbtube.log     │
 │                                                     │        │   └─ /, /search, /watch, /play  web │
 │  BlackBerry Browser ─▶ /play ─▶ Media Player        │        │  ffmpeg (libx264, aac_at)  cache/   │
 └─────────────────────────────────────────────────────┘        │  ImageMagick (length badges)        │
                                                                └─────────────────────────────────────┘
```

## 1. Toolchain: building a MIDlet with open-source tools only

RIM's own compiler (`rapc`) and `net_rim_api.jar` are closed source, and the official [blackberry/Eclipse-JDE](https://github.com/blackberry/Eclipse-JDE) repository contains only plugin source. A plain **MIDP 2.0 MIDlet**, though, runs natively on BlackBerry OS. Building one only needs:

| Step | Tool | Why |
|---|---|---|
| Compile | **Eclipse ECJ 3.33** (`-source 1.3 -target 1.1`) | The phone's JVM (CLDC 1.1) needs Java 1.1 class files. Modern `javac` can't target that anymore, but ECJ still can. |
| API | **MicroEmulator** `cldcapi11`, `midpapi20`, `microemu-jsr-135` jars | They replace the desktop JDK with the phone's API on the boot classpath, so using a desktop‑only class fails at compile time. |
| Preverify | **ProGuard 6.2.2** `-microedition` | CLDC only loads *preverified* classes (with StackMap attributes). ProGuard adds them, replacing Sun's old `preverify` binary. Shrinking, optimization and obfuscation are off. |
| Package | `jar` + `src/manifest.txt` | MIDlet-Name/Version/Vendor/Icon and the profile lines. |
| Descriptor | generated by `bbtube.py` at request time | The JAD must repeat the manifest's `MIDlet-*` lines exactly and give the exact JAR size, or the phone refuses the install. |

`build.sh` runs all of this. It then compiles `TestBBTube.java` against the built JAR and runs it on the desktop JVM, and finally runs `test_bbtube.py`.

Language limits that follow from `-source 1.3`: no generics, autoboxing, enhanced `for`, `String.format`, `StringBuilder` or enums. Collections are `java.util.Vector`/`Hashtable`.

## 2. The MIDlet

### 2.1 Structure

Everything is in one class, `BBTube extends MIDlet implements CommandListener, PlayerListener`, with three inner classes:

| Class | Role |
|---|---|
| `Row` | One list row: `kind` (SEARCHBOX, SECTION, ACTION, VIDEO, HERO, NOTE, FRAMES), `act` (what selecting it does), text, sub-text, video id, length, image(s). |
| `Screen extends Canvas` | A generic drawn list screen. Home, Results, Video and Preview are all `Screen`s holding different rows. It handles painting, the selection bar, scrolling and keys. |
| `VideoScreen extends Canvas` | The in-app player: header, video area, control bar, waiting states, seeking. |

Options is the one stock LCDUI `Form`, because it needs a real editable `TextField` for the server address.

### 2.2 Navigation and commands

- **Selecting a row** (trackpad click → game action FIRE, or Enter = key 10) calls `pick(Row)`, which switches on `row.act`: SEARCH_TYPED, RECENT, OPEN_VIDEO, MORE, PLAY, MEDIA_PLAYER or PREVIEW.
- **The BlackBerry menu** shows LCDUI `Command`s: Open/Search (OK, priority 1), Delete, More Results, Play, Play in Media Player, Preview Frames, Pause/Play, Options, Back. OS 6 places the OK‑type command with priority 1 first, so the menu opens on the action you'd expect.
- **Back** is a `Command.BACK`. `handle()` routes it as Player → Video → Results → Home, and on Home it first clears typed text.
- `commandAction` wraps everything in `try/catch Throwable` and reports errors. BlackBerry silently drops exceptions thrown from command handlers.

### 2.3 The Canvas UI ("native OS 6" look)

All screens are `setFullScreenMode(true)` Canvases painted by hand to match BlackBerry OS 6:

| Element | How it's drawn |
|---|---|
| Title bar | `gradient()` from `0x464646` to `0x121212`, a 1 px highlight line, the `logo.png` icon, a bold title, and an optional right-aligned status (*Buffering…*). |
| Rows | White background, `0xe3e3e3` separators, ink `0x1a1a1a`, secondary text `0x7a7a7a`. |
| Selection | Blue gradient `0x5aaaf3` → `0x1f69c9`. Text turns white. |
| Section band | Grey band with a small bold label (*Recent Searches*). |
| Search box | Rounded rectangle with a magnifier icon and a placeholder, or the typed text (the tail end when it's too long). It has a 2 px blue caret blinking every 500 ms. |
| Scroll bar | A thin indicator on the right when content is taller than the screen. |
| Icons | 7 small PNGs in `res/` (search, recent, more, media, preview, play overlay, logo). |

`gradient()` draws one horizontal line per pixel row, colour-interpolated with `mix(c1, c2, a, n)` (tested in `TestBBTube`). Text uses three fonts: bold medium (titles), plain medium (rows) and small (sub-text, times). Long titles are word-wrapped with `wrap()` (at most two lines, ellipsis) or shortened with `fit()`.

**Scrolling:** `step(dir)` moves the selection to the next selectable row, then adjusts `top` so that row is fully visible. Non-selectable rows (sections, notes) are skipped.

**Background thread:** one animation thread ticks every 125 ms. It turns the player's waiting spinner and, every fourth tick, toggles the caret. It repaints only the search box region, not the whole screen.

### 2.4 Typing on the home screen

Since 1.3.0 there is no `TextBox`. `Screen.keyPressed` on Home first calls `typing(key)`:

- Keys 8 or 127 (Delete) remove the last character.
- Printable keys (32–126 and 160–0x2FFF, which covers accented and CJK input) are appended, up to 100 characters. A leading space is ignored.
- After every change, `showHome()` rebuilds the rows: the search box, then *Recent Searches* filtered by the typed text (case-insensitive substring match).

Then `move(key)` handles navigation. It **ignores key codes 32–126** before asking `getGameAction()`, because on the 9780 letters also report game actions ('d' = LEFT, 'c' = DOWN, Space = FIRE).

### 2.5 Networking

`get(path)` performs every HTTP GET:

- URL is `"http://" + server + path + TRANSPORTS[i]`, where `TRANSPORTS = {";interface=wifi", ";deviceside=true;interface=wifi", ""}`.
- The first transport that connects is remembered in `transport`. When an option that worked stops working, the error is reported instead of moving on to the next option.
- If connecting needed a fallback, the earlier failures are logged to the Mac.
- All network calls run on background `Thread`s. The UI thread never blocks.

The API is **tab-separated text** (see [API.md](API.md)), split with the small helpers `lines()` and `split()`. There's no JSON parser on CLDC, and TSV costs almost nothing to parse.

**Images** are fetched one by one after the rows are shown, decoded with `Image.createImage(byte[], 0, n)`, attached to the row, and the row is repainted.

### 2.6 Persistence

| RecordStore | Contents |
|---|---|
| `bbtube` | The server address (`host:port`). Defaults to the `BBTube-Server` JAD attribute the Mac writes at install time. |
| `bbtube-recent` | Up to 8 recent searches, newest first, de-duplicated case-insensitively. |

### 2.7 The in-app player (`VideoScreen` + `playInApp()`)

**Preparation:**

1. `playInApp()` shows the `VideoScreen` with a *Connecting…* spinner.
2. A background thread polls `/api/play?v=ID` every 2 s:
   - `converting N` shows *Preparing video for BlackBerry* with a progress bar at N%;
   - `failed` shows an error;
   - `ready` continues.
3. `Manager.createPlayer("http://<mac>/v/ID.mp4;interface=wifi")`, then `realize()`.
4. `VideoControl.initDisplayMode(USE_DIRECT_VIDEO, canvas)`, then `setVisible(false)`, then `prefetch()`. The real video size is only known after prefetch.
5. `place(vc)` fits the video between the header and the 45 px control bar while keeping its aspect ratio, with `setDisplaySize`/`setDisplayLocation`. If that throws, it falls back to `setDisplayFullScreen(true)`.
6. `setVisible(true)`, then `start()`.

**Painting around live video:** direct video is an overlay the Canvas can't draw over. So `paint()` fills only the black margins around `(vx, vy, vw, vh)`, the header and the control bar, never the video rectangle. A once-a-second `tick()` reads `getMediaTime()`/`getDuration()` and repaints just the header and bar regions, so the video doesn't flicker.

**Control bar:** a dark gradient bar with a glossy blue rounded button (pause bars or play triangle), elapsed `m:ss`, a rounded track with a blue fill and a white knob, and `-m:ss` remaining. The duration comes from the player, or from the length the Mac reported when the stream doesn't say.

**Player events** (`playerUpdate`): STARTED, STOPPED (*Paused*), END_OF_MEDIA (*Finished*), `"bufferingStarted"`/`"bufferingStopped"` and ERROR update the header status and swap the menu's Pause/Play command. The buffering events are compared as **strings**, because the MIDP 2.0 stub doesn't define the JSR‑135 constants.

**Seeking (1.3.2):**
- Trackpad LEFT/RIGHT calls `seek(∓10)`. The target is computed from any pending target (so repeated presses add up), clamped to `[0, duration − 1 s]`, and shown on the knob immediately.
- A single background thread calls `setMediaTime()`. It loops until the target stops changing, because `setMediaTime` can block on the network.
- While a seek is pending, `tick()` doesn't overwrite the displayed time.
- A seek after END_OF_MEDIA clears the "ended" flag, so Play continues from the new point instead of restarting.
- The player ignores Delete (8) and printable keys 33–126, which also report LEFT/RIGHT on the 9780.

**Pause/resume** (trackpad click, Space or the menu) runs `stop()`/`start()` on a background thread.

### 2.8 Play in Media Player

`platformRequest("http://<mac>/play?v=ID")` opens the BlackBerry Browser on a self-refreshing *Preparing video… N%* page. When the conversion is ready, that page redirects to `/v/ID.mp4`, which the browser hands to the built-in Media Player.

`platformRequest` **must run inside `Display.callSerially()`**. Called straight from `commandAction`, OS 6 throws `IllegalStateException: UI engine accessed without holding the event lock`.

### 2.9 Diagnostics

- `log(msg)` sends `GET /log?m=<msg>` on a background thread. The Mac prints it to `bbtube.log` as `phone: …`.
- `logKey()` logs every key code and its game action, with *(player)* when sent from the player. This is how the trackpad codes were found.
- `report(what, e)` shows a friendly `Alert` (for example *Can't reach the Mac*) and logs the technical detail.

## 3. The Mac server (`bbtube.py`)

### 3.1 Server

A `ThreadingHTTPServer` on `0.0.0.0:8090`. `do_GET` maps paths to handler methods (a dict plus two regexes for `/vi/…jpg` and `/v/ID.mp4`):
- Broken pipes are ignored, because the phone hangs up when it stops or seeks.
- Any other exception becomes a 502 page instead of a dropped connection.

All inputs are validated:
- video ids must match `[\w-]{11}`;
- thumbnail sizes must be one of a fixed set;
- `/frame` only accepts Invidious `/sb/` storyboard paths and bounded crop boxes, so it can't be used as a general proxy on the LAN;
- log messages are truncated to 500 characters with newlines removed.

### 3.2 Talking to Invidious

`api(path)` is `urllib.request.urlopen("http://localhost:3000" + path, timeout=15)`. Endpoints used:

- `/api/v1/search?q=…&type=video&page=N&fields=videoId,title,author,lengthSeconds`
- `/api/v1/videos/ID?fields=title,author,lengthSeconds,formatStreams`
- `/api/v1/storyboards/ID?width=160&height=90` (WebVTT that points at sprite sheets)
- `/vi/ID/default.jpg`, `/vi/ID/mqdefault.jpg` (thumbnails)
- `/latest_version?id=ID&itag=18&local=true` (the 360p MP4 stream, proxied by Invidious)

The `fields=` parameter keeps responses small.

### 3.3 Conversion pipeline

The 9780's hardware decoder only plays **H.264 Baseline**, but YouTube's 360p MP4 (itag 18) is H.264 *Main*. With Main, the phone played the audio and reported "video format not supported". So each video is converted once:

```
ffmpeg -i <invidious itag 18>
  -vf scale=480:360:force_original_aspect_ratio=decrease:force_divisible_by=2  -fpsmax 30
  -c:v libx264 -profile:v baseline -level 3.0 -pix_fmt yuv420p -preset veryfast
  -b:v 600k -maxrate 700k -bufsize 1400k
  -af loudnorm=I=-16:TP=-3:LRA=11,aresample=44100  -c:a aac_at -b:a 128k -ac 2
  -movflags +faststart  -progress pipe:1 -nostats
```

| Choice | Reason |
|---|---|
| Baseline 3.0, ≤480×360, ≤30 fps | What the 9780's decoder supports; 480×360 is its screen. |
| 600 kbit/s capped at 700k | Smooth over the phone's Wi‑Fi, with good quality on a 2.4" screen. |
| `loudnorm` −16 LUFS, −3 dBTP | Loud modern masters peak at 0 dBFS and **crackled** on the 9780's AAC decoder. Levelling with headroom fixed it. |
| `aac_at` (Apple AudioToolbox) | With the same settings ffmpeg's native AAC encoder overshot to ~0 dBFS after decoding, while `aac_at` stayed near −2 dB. |
| `+faststart` | Moves the `moov` atom to the front, so playback starts before the whole file arrives. |
| `-progress pipe:1` | `out_time_us` lines are turned into a percentage (`progress_pct`, capped at 99) for the phone's progress bar. |

Job management:
- `conversion(vid)` returns `ready`, `converting` or `failed`, and starts a thread if needed.
- At most **2 encodes** run at once (a semaphore).
- Output goes to `ID.part` and is renamed to `ID.mp4` only on success.
- stderr goes to a temp file, because a full pipe would stall ffmpeg.
- A **1‑hour watchdog** kills a stuck encode.
- After each success only the newest **10** files are kept.
- Opening a video page (`/api/video`) starts the conversion early.

### 3.4 Streaming with Range

`/v/ID.mp4` serves the cached file with `Accept-Ranges: bytes`. It parses single `bytes=a-b`, `bytes=a-` and `bytes=-n` ranges (`byte_range`, unit-tested) and answers 206 with `Content-Range`, or 416 for an unsatisfiable range. The phone's player issues ranged requests when it starts and seeks, so seeking past what's buffered works.

### 3.5 Images

- **Thumbnails** (`/api/thumb?v=ID&size=80|120|160|192&t=4:57`):
  - Size 80 crops the letterbox off the 120×90 `default.jpg`; the other sizes scale the 320×180 `mqdefault.jpg`.
  - Re-encoded as JPEG with ffmpeg.
- **Length badges** are burned in with ImageMagick: a translucent black box with Arial Bold at `min(14, max(10, h/6))` pt, bottom-right, or a red **LIVE** box.
  - Phone fonts are about 22 px even at `SIZE_SMALL`, too big for a 67 px thumbnail.
  - Without ImageMagick the image is simply returned without a badge.
- **Preview frames** (`/frame?p=/sb/…&c=x,y,w,h&h=81&t=1:23`):
  - Invidious storyboards are WebP sprite sheets described by WebVTT cues.
  - `pick_cues` picks 6 frames spread across the video.
  - `/frame` crops one tile, scales it to the requested height and re-encodes it as JPEG with a timestamp badge. The phone can't decode WebP.

### 3.6 Install descriptor

`/app/bbtube.jad` is generated per request:
- it copies the `MIDlet-*` and `MicroEdition-*` lines from the JAR's own manifest;
- it adds `MIDlet-Jar-URL` (using the `Host` header the phone used), `MIDlet-Jar-Size`, and `BBTube-Server: host:port`.

So the app always knows where it was installed from, and the JAD can't drift out of sync with the JAR.

### 3.7 Web version

`/`, `/search`, `/watch` and `/play` are a no-JavaScript HTML version styled after OS 6. It uses solid colours first, then `-webkit-gradient`, so older browsers still get a usable flat look. It came first and is still useful from any browser. Its `/play` page is what *Play in Media Player* uses.
